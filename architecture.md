# Sweet v2 architecture plan/notes

## Stack

The backend is written in Go. The frontend is React with Tailwind and Lucide icons. It uses old Sweet's colours on old Sweet's dotted page background. The database is SQLite. There is no ORM. Typed queries are generated by sqlc, which runs as a Go tool dependency. Every query is a named statement in `internal/store/queries`, and handlers never contain SQL strings. The deployable unit is a single Go binary with the React build and the migrations embedded in it. The binary is small and portable. A Debian package would wrap it, and a self-hoster who does not want to use Docker can run it on its own. The distribution artefact is a very simple Docker Compose stack around the binary. The stack contains the binary, Caddy and Litestream. The Caddy is a custom build that includes the Cloudflare DNS module (see Domains).

Go was kept for the backend instead of using TypeScript end to end (see the Record section). Post bodies are the HTML that TipTap produces, sanitised by bluemonday (see Posts and editor).

**The stack as built on 2026-11-06, for a single instance that bootstraps itself.** The build produces one image from the `Dockerfile`. In that build, Node builds the frontend and Go builds the binary, both on Alpine, and Litestream's binary is copied from the Litestream image. The `deploy/` directory holds two Compose files. `compose.yml` runs the image with stock Caddy, which gets the domain's certificate through the HTTP challenge. `compose.proxied.yml` runs the image alone on a local port, for a host that already has a proxy. One such host is coraline, where the trial runs behind coraline's own Caddy. The xcaddy build with the Cloudflare DNS module stays with the orchestrator, because the orchestrator is the component that needs a wildcard certificate (agreed with Raphael, 2026-11-06). The container's entrypoint connects the parts. When a bucket is configured, the entrypoint has Litestream restore the database if the disk has none, and then runs the binary under `litestream replicate -exec`. When no bucket is configured, the binary runs alone. A host with the Compose file, the `.env` file and an empty disk therefore starts up as the instance whose data that bucket holds. This is what self-bootstrap means. Every setting the operator chooses is in one `.env` file (`deploy/env.example`). It holds the domain, the SMTP settings and the bucket. The README is the install guide. It is written to be followed from top to bottom by someone who has never seen the code.

## Licence

The server and the React app are licensed AGPL-3.0-or-later. There is no CLA. Contributions are accepted under a DCO sign-off. The API client and the shared types live in their own directory under the MIT licence, so that alternative clients can exist. By default, the binary shows a "Source code" link in the footer. The link is configurable, like Mastodon's `source_url`. The link satisfies the obligation to offer the frontend's source to the people it is served to. A self-hoster who modifies the software points the link at their fork.

This choice has a known cost, and the cost was accepted deliberately. Without a CLA, the project can never be relicensed as source-available. This audience wants that guarantee as a signal that the project is credible.

## Shape of an instance

Each instance is one social community with one feed and one chat room.

**Topics** are filters on the feed. They are not sub-groups with their own membership. A topic is a label on a post. A post has at most one topic, and most posts have none. A topic is never required, and a topic is not a separate place to post, because having to choose the right place before writing puts people off posting at all. A user can open a topic to see only its posts. A user can also follow a topic, so that new posts in it are sent to them as notifications and in the digest. Following a topic changes which posts are sent to the user. It does not change who can see which posts.

**Built on 2026-11-07, following the drawings made with Raphael.** Topics exist only on the community's feed. The root group's owner and moderators manage them on the Community page (`perm.ManageTopics`). A topic has a name of up to 40 characters, unique case-insensitively, and an optional one-line description. Topics are listed alphabetically, so there is no order to maintain. Topics are off when the list is empty. There is no flag for this. No topic control appears anywhere until a topic exists. A post in a room has no topic. A request that sets a topic on a post in a room gets 400. **A topic is shown as the same pill everywhere.** On a post, the pill comes after the time in the author line, so the line reads who, when, where. The pill opens the topic, for every user. At first the pill was at the right of the row. There, the empty square of the menu that appears on hover sat beside it, and the user's own posts and other users' posts lined up differently. Raphael moved it late on 2026-11-07. The author changes a post's topic while editing the post, with the topic pill in the edit form. For an hour, the pill on a post opened a menu for changing the topic, for the author and for the staff. Raphael said on 2026-11-07 that, with the topic in the editor, a badge that is also an edit control is confusing. `perm.SetTopic` still lets the root group's staff move anyone's post to another topic. This was agreed as the one thing staff may change on another user's post, because assigning a topic is moderation, not editing. No control uses it yet. The feed header is the header strip of the composer card. It is the same full-width band with a hairline below it that a post uses for "Posted in". The pill in it reads Everything, or the selected topic's name, and opens the topic menu. While a topic is selected, its description is shown under the pill, and a Subscribe button is shown at the right. Subscribe is the word users see for following, and the word is Raphael's choice. The button is a ghost toggle. Once pressed, it reads Subscribed in Sweet red. On hover it reads Unsubscribe. The topic pill belongs to the feed, not to the top bar. The top bar names the current view and holds that view's controls. On a desktop the top bar also spans the chat, so a pill in the top bar looked as if it applied to both the feed and the chat. The pill is also not in a card of its own. When the feed was set to Everything, such a card was an empty box around one small control. Three placements were tried in screenshots before this one (Raphael, 2026-11-07, evening). The feed's topic filter is part of the URL (`/?topic=<id>`), so a link to a topic view can be shared. The composer has no topic control. Raphael removed the "Set topic" pill from the composer on 2026-11-08, a day after it was added. A new post gets the topic the feed is currently filtered to, or no topic. When a topic is selected, the composer's placeholder text names it. The topic is selected with the pill in the feed header. The edit form keeps a topic pill after the toolbar, because the edit form is the only place where an existing post's topic can be changed. The editor's footer has the formatting toolbar on the left, and Cancel and then Post or Save on the right. When the pane is narrow, the Cancel and Post or Save buttons wrap onto their own right-aligned line (`Row push="end"`). A topic has one shape everywhere, and the tag icon is part of that shape. The shape comes in two sizes. The smaller size is a label on a post. The larger size is a control, in the feed header and in the edit form. A room's feed has none of these topic elements. The schema is `topics(id, name, description)`, a nullable `posts.topic_id`, and `topic_follows(user_id, topic_id)`. The endpoints are as follows. `GET /api/topics` returns the topics, with `following` for the viewer and the counts that the owner's list shows. `POST`/`PUT`/`DELETE /api/topics[/{id}]` are for staff. `PUT`/`DELETE /api/topics/{id}/follow` follow and unfollow a topic. `POST .../posts` accepts `topic_id`. `PUT /api/posts/{id}/topic` changes a post's topic. The root feed accepts `?topic=`. The events are `topic` and `topic_delete`. They are sent to the whole instance, like `settings`. A post event already carries the post's `topic_id`. The client looks up the topic's name in the topics cache at render time, as it does for authors' names, so a rename updates every pill at once. Deleting a topic removes the topic from its posts and deletes its follows. The confirmation dialog states both, with the numbers. When a post is created in a topic or moved to a topic, each follower of the topic except the author gets a `topic_post` notification. The notification carries `topic_id`, so that its text can say "posted in Practice". A topic filter in search and manual ordering of topics are not built. The digest reports the week's post counts by topic (2026-11-08).

**Tags** are freeform, and a post can have many. They are typed as `#hashtags` in the body. A tag says *what* a post is about. There are tag pages and tag search. Tags have no subscription and no curation. Old Sweet's data shows that 312 tags were used. The rituals people remember, #hellosweet, #WhatILikeToRead and #DailyRPGQuest, were all hashtags that nobody set up. Technically, a tag is a `hashtag` node in the TipTap schema. The walker extracts it into a tags table, as it does for mentions.

Comments on a post are a flat list. They are not threaded. A reply to a specific comment is a quote-reply, as in chat.

An instance has both live chat and long-form, blog-like posts, with inline image uploads and embeds.

### Groups

**In the user interface, a group is called a room** (Raphael, 2026-11-05). The nav has a Rooms section, and the interface has New room, Room settings and Leave room, at `/r/<id>` and `/rooms/new`. In the interface, a DM is called a conversation. The word "room" describes what the thing is, a space with a chat in it. The word "group" described a set of people. The code, the tables, the API (`/api/groups`) and this document keep `group` as the name of the object, because the root group and a DM are also groups and are never called rooms. The word is changed only where a user reads it. Renaming the identifiers across the schema, the API and both codebases is a separate mechanical job, and it has not been done.

A group is a space scoped by membership. It has the same structure as the instance, a feed and a chat room, and it is drawn with the same panes and editors. **The instance itself is the root group.** Every user joins it on registration, and nobody leaves it. "Everyone sees everything by default" is therefore implemented as membership of the root group, and no query treats it as a special case. Every post and every chat message belongs to exactly one group. A comment belongs to its post's group.

Groups are **private and invisible**. A group, its name, its members and its content exist only for its members. There is no list of groups and no "ask to join" action. Users join a group only by being added. If a group wants to be found, its staff announce it in a public post, and users ask to join in a DM. On 2026-11-04 a "listed" setting was considered and dropped. It would have shown a group's name to the whole community while keeping its content and members private. Old Sweet's data argues against the kind of group it would produce (see below). A group can also be made findable at no cost by posting about it. The instance's owner and moderators see only the groups they are members of. A private group is private from the instance's owner too. Moderation of a private group happens when a member reports something, which explicitly brings in staff. The rules page says this.

A group has **one setting, its mode**. The mode is posts, chat, or both. The mode is chosen when the group is created, and the group's owner can change it. A DM's mode is chat only, and it cannot be changed. The root group's mode is the instance's posts and chat feature flags. There is no second mechanism.

**A group always has an owner.** A group has exactly one owner while it has any members. Ownership changes in only two ways. In the first, the owner explicitly hands ownership to another member and becomes a moderator. An owner may leave the group only after handing over ownership. In the second, the owner's membership ends in some other way, because their account was removed from the instance or deleted. Ownership then passes by seniority, to the longest-serving moderator, or, if there is none, to the longest-serving member. A moderator leaving changes nothing. When the last member leaves, the group is deleted. There is no vote and no takeover. A moderator becomes owner only by the owner's own action, or by being next in line when the owner has left the instance entirely. Only root staff can cause the owner to leave the instance in that way. In that case the group passes to its own longest-serving member, never to the staff member who removed the owner. The root group's owner cannot leave, and nobody can remove them. If that account is lost, the binary's `-owner` flag appoints a new owner.

When a user is added to a group, the group appears in their nav at once, and a new DM appears on their Messages page. Both are delivered by a `membership` event. When a user is added to a room, they also get a notification (see Notifications).

**Groups repeat the instance's role structure, one level deep.** A role is a property of a membership, not of a user. Every group has one owner and any number of moderators, and the other members are plain members. The instance's owner and moderators are the root group's owner and moderators. There is no other kind of role. In any group, the owner and moderators can delete anything in the group, and they cannot edit anything written by others. The owner and moderators add and remove members. Nobody can add members to a DM, because a DM always has exactly two people (see below). Only the owner sets roles and hands over ownership. Only the owner renames the group, sets its mode, or deletes it. A user's role in one group has no effect in another group. For example, the instance owner is a plain member of a clubhouse they were added to. Every rule in `perm` takes the actor's role in the group that the object belongs to.

Any user may create a group, unless the instance's `group_creation` setting allows only the root group's staff to create groups. `group_creation` was the instance's first setting, and its values are anyone or staff. The creator of a group is its owner. The setting is stored in a `settings` table of keys and values, and the root owner edits it. It is exposed as `create_groups` in the root group's `can` flags, so the client learns it in the same way it learns everything else. Members may leave any group except the root group. There is no pending-invite state and there are no join requests.

A room may have a **picture** (Raphael, 2026-11-06). The picture is an uploaded image. The owner sets it from Room settings, in the same kind of row that a user's picture has on Settings (`PUT /api/groups/{gid}/picture`). Setting it is checked by the same `perm.Rename` call as naming the room. A conversation has no picture, because it is shown as its other person. The picture is carried on the group and on the group's event. It is visible to the room's members in the same way as a post's images. The image sweep does not delete it. It is drawn in place of the tile wherever the room's mark is shown. **A post shown outside its room has a header that names the room**, as old Sweet did for a community's post on the home timeline. The header is a full-width strip across the top of the card. It holds the room's tile or picture and "Posted in <room>", with a hairline below it (`Card head`). The room name links to the room. The header shows on a user's profile page and on a post's own page, where posts from different rooms appear together. Inside the room there is no header, because the page is already the room. A **DM** is a group of kind `dm`. It has no name and exactly two members. Each member sees it under the other member's name. A DM is created from the Message action on a user's name, or from New message. If the two users already have a DM, it is reused. **A conversation has exactly two people** (Raphael, 2026-11-06, on a walk). For more people, users make a room. The two-person rule is one check on the server. The request's `members` must be exactly one other user, or the server returns 400. The data model did not change. A conversation is stored in the room tables, so it gets chat, markers, events, visibility and hiding without a second code path. A separate table for pairs would have given messages, markers and the stream filter a second parent. The rule removed a day's worth of edge cases. It removed the many-person To list, the count on the stack of profile pictures, a conversation's own People page with its list of people who had stepped out, the "New conversation with these people and others" action, and the question of what a conversation of three becomes when one of them leaves. A conversation has no members page. `/r/<id>/members` redirects to the conversation. The conversation's top bar names the other person and holds a three-dot menu with Hide conversation. It has no people button. Migration 012 closed the conversations of three or more people that had been created the afternoon before. A conversation uses the same tables, the same rules and the same panes as a room, with the posts pane closed by default. **A conversation is defined by its people, and each person's presence in it is their own** (Raphael, 2026-11-05, evening). A conversation's identity is the set of people it was opened for. The set is fixed, and there is one conversation per set. The set is stored as `groups.people_key`, the sorted user ids, which is unique among live conversations. Opening the conversation with a user, from New message or from their card, finds the existing conversation or creates it. This happens inside one transaction, so two requests to open it cannot create two conversations. Nobody can be added to a conversation (`perm.AddMembers` is false for a conversation). A message to a different person goes in the conversation with that person, or in a room. Presence is stored in the membership's `hidden_at` column. It is null while the conversation is on the user's list, and it is set while the user has hidden the conversation. Either person in the conversation can hide it with Hide conversation, in the top bar's menu. Hiding it removes it from that user's list and removes the client's cached data for it. The response to the Hide request is the updated membership, so the user's own Messages page lists the conversation under Hidden at once. Hiding affects only the user who hides. The other members are not informed, neither on a page nor through the event stream, in the same way that archiving a chat informs nobody. The conversation's name does not change, because its people have not changed. Messages sent while it is hidden are still sent in that conversation. The user sees them when they open it again, from All messages (the Hidden list at the bottom), from a user's card, or from New message. Nothing is deleted. A conversation that every member has hidden still exists. The first version used the words "Leave" and "stepped out", and showed them to the other members. On the same evening, this confused the one person who saw it. "Leave" promised a removal that cannot happen. Informing the other members explained the absence to the wrong people. Rooms are not affected by this. Leaving a room deletes the membership row, and when the last member leaves, the room is deleted. The test that separates rooms from conversations is whether the thing continues to exist when its people change. A clubhouse does, so it is a room. A private exchange with one person does not, so it is a conversation. On the same evening, this replaced an earlier rule, "a DM grows by its own people". Under that rule, adding people to an existing DM turned the conversation into a room without a name. The set {ABC} minus C could not be told apart from the pair {AB}. The same set of people could recur as a new room, and two rooms could hold the same three people. Two other options were considered on the way and not taken. With rooms only, a conversation could no longer be addressed by its people, and the owner of a pair would have to hand over ownership before leaving. With conversations only, there would be no way to have a clubhouse. In the nav, conversations are in their own Messages section after the rooms. The section shows the latest five. Each conversation is drawn as a room is, but marked by its people's profile pictures (see Layout). Because a DM is named after its people, every response and event that carries a group is built in one place on the server (`wireGroup`, or the creation path). A DM therefore always reaches the client with its members. On 2026-11-05 a response without the members made a DM show "Just you" until the next refetch.

Three needs drove this design. The first is a moderation room where staff talk and share screenshots. The second is a small invite-only clubhouse inside a larger community, for a subject its members want to keep among themselves. The third is a private conversation with one person.

This is what old Sweet's data says about groups. The figures come from the dump, which covers 53 communities and 3,038 posts from March 2019 to October 2021. Communities carried 18% of all posts. Communities had a visibility setting (39 public, 14 private) and a join type (43 open, 10 by approval). They also had membership requests, bans, mutes, rules and vote-based moderation. Measured by activity in the final six months of the data, 4 of the 39 public communities were active, and 0 of the 14 private ones were active. 0 of the 10 approval-join communities were active, and their median membership was 2. The largest private community had 42 members. Its members posted 22 times, and it became inactive within five months. So the data does not show that private groups worked where public ones did not. Private and approval-join communities did worse. The data cannot show whether a group whose content could not be posted anywhere else, such as a moderation room or a DM, behaves like a community that competes with the feed for ordinary posts. Such groups are functional spaces that are used when needed. For them, a period with no activity does not mean the group has been abandoned. That distinction is an opinion. The design therefore starts from the functional cases. A support group that people can find is treated as an experiment, not as a basic assumption of the design.

The instance's feature flags (posts, chat, images) also apply inside groups.

### Feature flags (per instance)

Feature flags are stored in an instance settings table. Each feature is on or off. The owner sets the flags during onboarding and can change them later. The features are long-form posts, chat, images, embeds, and alt text. Topics have no flag. They are off while the topic list is empty (see Topics). Alt text has three values (off / optional / required). The API refuses requests that use a disabled feature. The frontend reads the settings at startup and hides disabled features. This is how one product serves a friend group, an interest community and a chat-first group.

### Realtime

Clients receive updates over SSE, and they send through plain POST requests to the API. Both are plain HTTP, so cookie authentication and proxies work without extra setup. Caddy detects `text/event-stream` and flushes immediately, with no configuration. Each client has one stream, which carries every event type (chat, posts, replies, notifications, version). Socket.io is not used. WebSockets should be reconsidered only if presence or typing indicators are wanted.

Every event has an `id:` line that holds the event log's integer sequence number. When the browser reconnects with its own `Last-Event-ID`, the server answers directly from SQLite. `?since=<seq>` runs the same query when the client reconnects manually. An explicit `since=0` replays the log from the start. The replay ends with a `: caught up` comment line. Browsers ignore comments, and the Go tests read up to that line. A client that gives no sequence number has just loaded the page from the API, and it receives only events that happen after it connects. There is no in-memory replay buffer. SQLite serves as the buffer.

**Each resource has one builder, and every write re-reads its row.** Each resource gets its wire shape from exactly one function in `internal/api/wire.go` (`wirePost`, `wireComment`, `wireMessage`, `wireMembership`, `wireGroup`, `wireUser`). The function builds the shape only from the store's row for that resource. A handler that writes then reads the row back inside the same transaction and passes it to the builder. The response and the event are the builder's output. They are never a struct that the handler assembled from the data it already had. List handlers convert their list rows to the single-row type, and the compiler checks the conversion field by field. Personalisation for a viewer (`can`, `role`) happens once, as the data is sent, in `forViewer`. This is tested as a property. For every write, the response and the viewer's event must be deeply equal to a fresh fetch (`TestRepliesAndEventsMatchTheRow`). This removed a class of bug that had caused three bugs in two days. Each of the three was a hand-built payload with a missing field. One was a group without its flags, one was a DM without its people, and one was a membership without its joined time. Before this, the convention was that "events carry the whole thing", but nothing enforced it.

**Each resource has at most two event kinds.** `post`, `comment`, `message`, `user`, `group` and `membership` each carry the whole resource and mean "this is its current state". Creating and editing send the same event. `post_delete`, `comment_delete`, `message_delete`, `group_delete` and `membership_delete` carry ids. A comment's delete event also carries its post's id. A membership's delete event carries the group id and the user id. `notification_delete` carries `{user_id, before}`. It means every notification of that user up to that time. This is an exact set, so one event is sent instead of one event per row. `marker` has only one kind, because a marker is upserted, only moves forward, and is never deleted. There are no other event kinds. The client cache therefore has exactly one upsert and one delete per resource. A new feature adds a resource, not a new event kind. This reversed an earlier design with `post_edit` and `comment_edit` events, because such kinds kept multiplying.

**The stream is filtered per viewer.** The log stores every event once. Before writing an event, each connection checks it with `CanSee` for that connection's viewer and adds the viewer's `can` flags. An event for a group the viewer is not a member of is never sent. When the viewer is added to a group, a `membership` event arrives, and the client then fetches that group. When the viewer is removed, a `membership_delete` event arrives, and the client then drops the group.

Reconnects are common on mobile. The test case is a UK train. iOS also closes background SSE sockets without any signal. On iOS 18 the `error` event does not fire and `readyState` stays OPEN while the socket is dead, so the browser's automatic reconnect never starts. The client and the server therefore do the following.

- The server sends a `:` heartbeat comment every 15 s. The client treats 30–45 s of silence as a dead connection. Writing the heartbeat also lets the server detect dead clients and free their goroutines. If the domain is ever proxied through Cloudflare, the heartbeat also keeps the stream open past Cloudflare's 125 s read timeout.
- On `visibilitychange`, `pageshow` and `online`, the client closes and recreates the EventSource and resyncs, whatever the `readyState` is.
- The client records the last event sequence number it has seen on each stream, and it resyncs on every reconnect.
- **There is no offline posting.** The client detects that it is offline when there has been no heartbeat for 30 s or `navigator.onLine` is false. It then shows an offline banner and disables sending. If a send fails anyway, the text stays in the composer with a retry button. There is no send queue, and there are no client-generated ids.

Each idle SSE connection costs one goroutine and tens of KB of memory. 500 connections are an insignificant load. HTTP/1.1's limit of six connections per host does not matter behind Caddy, which uses HTTP/2. A self-hoster who puts an HTTP/1.1 proxy in front of the binary, or serves plain HTTP, shares six connections between the stream and proxied images. This needs one line in the self-hosting documentation.

### Posts and editor

The editor is TipTap, with a small schema (paragraph, heading, text, bold, italic, link, mention, hashtag, image, embed, lists). **The body is HTML.** It is TipTap's own output (`editor.getHTML()`), sanitised on the server and stored once. There is only one body format, now and in the future. TipTap loads HTML back into the editor natively. HTML is the library's default content format.

**HTML only, with no JSON column (this was debated again and confirmed).** The schema is what creates lock-in, not the storage format. HTML also degrades more gracefully. ProseMirror JSON is meaningless without the exact set of extensions and attribute names. HTML renders in any browser, and it can be imported into any editor if TipTap is ever replaced. Old Sweet's database had four body formats from three editor changes, and the HTML column is the one that still renders. Storing JSON as well would create a second source of truth that cannot be validated and that would drift from the sanitised HTML. This should be reconsidered only if collaborative editing (Yjs) is ever wanted. A round-trip fixture test in the frontend guards against TipTap upgrades that change serialisation. The test checks that `setContent(html)` followed by `getHTML()` returns the input, after normalisation. TipTap versions are pinned and upgraded deliberately.

To edit a post, the client loads `body_html` into the editor with `setContent`. The user edits it, and the output of `getHTML()` goes back through the same sanitiser. The whole body is the unit of editing (`PUT /api/posts/{id}`, author only, which sets `edited_at`). There are no diffs and no versions. Connected clients receive a `post` event carrying the full post, and they replace the post in place. The sanitiser accepts TipTap's link attributes (`target="_blank" rel="noopener noreferrer nofollow"`) unchanged. Stored HTML is therefore byte-identical to the editor's output, and loading and saving a body without changes returns the same bytes (a fixed point). A Go test (`TestFixedPoint`) and the frontend round-trip test share their fixtures.

**bluemonday checks every body.** Every body (post, comment, chat message) passes through one bluemonday policy before it is stored. The policy *is* the schema. It lists the allowed tags and attributes. It limits `href` to http, https and mailto. It forces `rel="noopener noreferrer"` on links. It allows no `class`, `style`, `target` or event attributes. It allows `data-mention-id` on `span` only when the value matches a UUID pattern, and `data-image-id` on `img` only when the value matches a UUID pattern. It limits `src` on `img` to our own `/img/<id>` path, and it allows `data-embed-url` only with http(s). Nothing the client sends is trusted before it passes the policy. Everything that has passed the policy is trusted. Body size has hard limits.

**The @ suggestion list offers only the members of the group** (Raphael, 2026-11-08). In a room it offers the room's members. In a conversation it offers both people. On the community feed and in a bio it offers all users. `BodyEditor` takes the group id and reads the members from the cache. Before this change the list offered every user everywhere, so people who could not see the room could be mentioned. The server already sends no notification to a non-member, so such a mention was plain text with no effect. The list is positioned one animation frame after it opens, because the editor lays out the @ marker after the suggestion plugin's callback returns. Positioning the list immediately placed it at the left edge of the window when only @ had been typed.

**Extraction** runs Go's standard HTML parser (`x/net/html`) over the sanitised body. It extracts mention ids (for notifications), hashtags (for the tags table), and plain text through bluemonday's `StripTagsPolicy` (for the search index, and for the digest if that is ever needed). It is a loop over a tree, not a schema walker.

**Rendering on the client** inserts the sanitised HTML as it is. This is safe because bluemonday has already run. It is the one place where `dangerouslySetInnerHTML` is allowed, and it is wrapped in a single component.

Images are `<img data-image-id="…" src="/img/<id>" alt width height>`. There is no gallery markup. Adjacent images are rendered as a gallery. The `src` is a server path, not a storage URL, so the storage can be moved without changing posts. An image is uploaded when it is inserted. An hourly sweep (`images.Sweep`) deletes images older than a day that no live post, comment, message or profile picture references. This covers abandoned drafts, images removed while editing, and the pictures of deleted posts.

Mentions are `<span data-type="mention" data-mention-id="uuid">@name</span>` (built 2026-11-06). Typing @ in any editor offers the members of the group the text is written in. This uses TipTap's Mention extension with its suggestion list, positioned by Floating UI. The client renders each mention with the user's current name, taken from the users cache at render time. This happens in `content/decorate.ts`, inside the `Body` component that renders every body. Renaming a user therefore breaks no mention. The name is a link to the user's profile page, routed inside the app. The server extracts the ids from the sanitised body (`sanitize.Mentions`, a walk of the tree from `x/net/html`). Each mentioned user who is a member of the group and is not the author gets a `mention` notification. For a mention in a post, the notification links to the post's page. When the post's author is mentioned in a comment on their post, they get only one notification, the comment notification. For a mention in a message, the notification links to the room. Editing a body does not send new mention notifications. A mention of someone outside the room is only text, because that person could not see it. Hashtags are on hold. On 2026-11-06 Raphael asked, "tags are just topics though, aren't they?" The decision between tags and topics comes before either is built. Until then, a #word is plain text.

**How a post is drawn.** Raphael chose this layout from three drawings on 2026-11-06. The author line comes first. The body is 8px below it. The comments button is 16px below the body, with space beside it for controls that come later. When the thread is open, the thread is 16px below that, on its own background. The thread background is a light warm grey panel inside the card (`--color-ground`). It is lighter than a form field and has no border of its own. Raphael chose it because it is "friendlier". The panel holds the comments, oldest first, with a hairline between each. Comments are one size smaller than the post. Comment text is 15px against the post's 16px, and so is the commenter's name. Each comment has a 20px profile picture. The panel has 12px of padding on every side. The reply box is at the bottom of the panel. It is the only white element in the panel, and it says whom it replies to ("Reply to kit…"). The single panel shows where the post ends, and the white reply box shows where to type. Two drawings were not chosen. One was old Sweet's layout, a grey box for each comment under its author. The panel keeps the intent of that layout with fewer visual elements. The other was a blush-coloured line down the margin, with the comment count written as a sentence. On a device with a pointer, the three-dot menu on a post, a comment or a message is hidden until its block is hovered or has focus. This is implemented as `Menu reveal`, and it works by level. A post's menu shows while its card is hovered and no comment in it is hovered. A comment's menu shows while its own article is hovered. A message's menu shows while its own row is hovered. The first version used the nearest hovered block, and hovering a post's card showed the menu of every comment in it (2026-11-06). A touch screen always shows the menus, because users cannot discover a long press and the dot is small. The menus are hidden to reduce visual noise. Otherwise a room of messages or a thread of comments shows a column of identical dots.

**A post has its own URL** (Raphael, 2026-11-06). The URL is `/p/<id>`, served by `GET /api/posts/{id}`. Like every other path, it returns 404 to users who are not members of the post's group. The page shows the post with its thread open, under a top bar that says "Post by <name>". The bar links back to the room the post is in. That room stays mounted behind the post page, in the same way as the room behind a members page. A post's time in the feed is the link to its page. The link is a real anchor that wouter routes, so it can be copied or opened in a new tab. `Link` in `web/src/ui` distinguishes a path inside the app from an external URL. The post page has its own query for the post. The query is seeded from a loaded feed, so the page renders at once. `applyEvent` writes every change that reaches the feed into that query too. These changes include an edit, a new comment count, an author's new picture and a deletion. The feed and the post page therefore never disagree. Notifications link to this page. There is no other way to link to a post.

Drafts are saved automatically to the browser's local storage, not to the server. This has a known limit. Safari deletes all site storage after 7 days without a visit, for sites not installed to the home screen. Installed PWAs are not affected. This limit is accepted.

### Chat

Chat messages use a subset of the same TipTap schema (paragraph, text, link, mention, hashtag, emoji), with a minimal TipTap composer. They pass through the same bluemonday policy. There is therefore one body format and one extraction path across the product.

A reply is stored in a `reply_to` column on messages. It is rendered as a quoted snippet above the reply. Replies stay in the room's flat list of messages, as in WhatsApp and Telegram. There are no Slack-style threads, because they would turn the room into a second feed.

A message is the same kind of content as a post or a comment, with the same ownership rules. Its author may delete it, and so may the group's owner or a moderator (`perm.DeleteMessage`). Nobody can edit a sent message. Deletion is soft, and it reaches clients as a `message_delete` event. A message's menu sits at the top right of the message's own block. This applies to the first message of a run too. The menu is never on the author line above the run. It stays at the top right however tall the body is and however much it wraps. In `MessageBlock`, the body keeps space free on the right, and the menu is absolutely positioned. A hovered message gets a blush background. Raphael set this placement and the blush on 2026-11-06. This corrected the previous day's rule, "on the author line for the first message", which was Raphael's own mistake. A menu never makes a block taller, so a run of messages keeps its 4px spacing. Before that, for one day, the menu was beside the line, in a flex row. The flex row shrank the body before the menu moved, and once a wide picture pushed its own menu underneath itself. A Playwright check on the element boxes found this on 2026-11-05.

The layout is one page under a top bar. A collapsible nav column is on the left. Posts and chat come next, each scrolling independently, with a draggable divider between them. The default ratio is 2:3, clamped between 1:3 and 3:2. Dragging a pane past the edge collapses it into a thin vertical rail, and the rail reopens the pane. A pane scrolls from its top edge to its bottom edge. Its margin is inside the scrolling area, on the content, not on the pane (Raphael, 2026-11-06). The pane widths and the open panes are saved per browser. Below 800px wide, the nav column is removed and one pane shows. A bottom tab bar holds Home, Search, Notifications and a Menu item, in that order. The menu page holds what the nav column holds, with the account at the top and Sign out at the bottom.

**Every view has a bar across the top, on the phone and on the desktop** (Raphael, 2026-11-06). This reversed the earlier "no header" rule. The bar names the view (Home, the room, Messages, Settings, Post by so-and-so). When the view sits under another view, as a room's members page or a post page does, the bar links back. The bar holds the view's controls, which never wrap. When space runs out, the title shrinks first and is truncated to one line. On the phone, the switch between a group's Posts and Chat is in this bar, as icons. Posts and Chat are two views *of* the same group, not separate destinations. The tab bar at the bottom holds only destinations and tools. The reason is that when Posts and Chat were in the phone's tab bar, a room's chat could not be told apart from Home's chat. The tabs also looked like more destinations in the app, rather than two views of the room the user had just opened from the menu. Pages have no title of their own. ### Embeds and link previews

An embed is an `embed` node that stores only the URL. The server fetches the metadata, using oEmbed where the provider supports it and OpenGraph otherwise. It stores the title, the description and a thumbnail copied into our S3 storage. It renders a click-to-play placeholder. The YouTube or Vimeo iframe loads only when it is clicked, so third-party trackers are not on the page by default. Providers on an allow-list get a player. Every other URL gets a link card. A bare URL on its own line becomes an embed automatically. The same fetcher produces link previews.

To prevent SSRF, the fetcher uses an HTTP client library that is safe by default (for example `doyensec/safeurl`) instead of our own checks. The library handles private and link-local address ranges, including cloud metadata addresses, as well as IPv6, DNS rebinding and redirects. It is one import. The response size and the total time are capped. This client is never reused for the S3 endpoint, because a self-hoster may legitimately run that endpoint on a LAN.

### Images

Uploads go through one storage interface with two drivers. The first driver is a local directory. It is the default, and it is what development and a self-hoster without a bucket use. The second driver is S3-compatible storage (Cloudflare R2 for hosted instances). It is chosen when the endpoint and the bucket are set in the config. Images are large and R2 space is cheap, so hosted instances always use R2. This reversed an earlier plan, "S3 only, local later". A local default costs forty lines of code and removes the need for a bucket on the first run.

An open question is how to isolate hosted instances from each other in R2. Today the protection is each instance's own `images` table. The only way to reach an object is through `/img/<id>`, which is looked up in that table, and the sweep deletes only the instance's own keys. The bucket credential itself can read every prefix. R2 scopes tokens to buckets, not to prefixes, so the credential cannot enforce isolation within a shared bucket. One bucket and one token per instance can enforce it. The Operations section already assumes one bucket per instance for Litestream. This must be decided before the second hosted instance.

The accepted input formats are JPEG, PNG, WebP and GIF. The server detects the format by its magic bytes, not by the file extension or the declared type. Any other format is rejected with a clear message. Generated sizes are output as JPEG or PNG only, because Go's `x/image/webp` decodes WebP but does not encode it. GIFs pass through unchanged.

HEIC is not decoded. The file input uses `accept="image/jpeg,image/png,image/webp,image/gif"`, with JPEG first, and never `image/*`. WebKit transcodes a chosen HEIC file to the *first* type in the list. If `image/*` appears anywhere in the list, WebKit sends the HEIC file as it is. Android does not transcode. The magic-byte check catches the HEIC file and returns the clear message.

On upload, the server applies the EXIF orientation, strips metadata and generates sizes. Display pictures use the same pipeline with fixed square sizes.

Images are protected per instance. The Go backend serves them at `/img/<id>`, with a session check and `CanSee`. An image is served if the viewer uploaded it, or if the viewer can see a live post, comment or message that references it. A screenshot in a private group is served only to that group's members. No images are used outside the web app, because the digest carries no content. So there are no signed URLs.

In the editor, each image is a card. The card shows the picture small on the left, the alt text field in the rest of the card, a grip to drag the card between blocks, and an X to remove it. There is no prompt when an image is inserted. Adjacent cards join into one block labelled "Gallery of N images", because the post renders a run of adjacent images as a grid. Two images are laid out 2 across. Three are 2 then 1. Four are 2 and 2. Five are 2, 2, 1. Six are 4 then 2. Seven are 4, 2, 1. Eight are 4 and 4. A gallery holds at most eight images, and a longer run is split. The gallery exists only at render time (`wrapGalleries` in the frontend). The stored HTML is a plain run of `<img>` elements. Chat has no inline images. In chat, pictures are attached above the text field as the same cards, and they are sent as a block of `<img>` elements before the text. Whether alt text is required is a feature flag.

A post's three-dot menu (Floating UI) holds Edit and Delete, as the post's `can` flags allow (see Permissions). Comments have the same menu. Delete asks for confirmation first, in the browser's own dialog element. Deletion is soft (`deleted_at`). The post is removed from every list. Its comments are removed with it, because they can only be reached through the post. Its images are deleted by the next sweep. A `post_delete` event carrying the post's id makes open pages remove the post.

There are size limits per image and per post. A per-instance storage quota is enforced at upload. The quota can also be used to set pricing.

## Data model notes

- Ids: every row has a UUIDv7 id. The reason is a possible future merge of two instances' data. With these ids, a merge is an insert rather than a renumbering of every reference, including the references inside post bodies.
- Event ordering: the event log has an integer sequence column. The sequence is assigned inside the write transaction, so it follows commit order. SSE `id:` and `?since=` use it. UUIDs are not used as cursors, because with a connection pool the order in which UUIDs are generated is not the commit order.
- Every write transaction starts with `BEGIN IMMEDIATE`. A deferred transaction that reads and then writes can fail with `SQLITE_BUSY_SNAPSHOT`, and `busy_timeout` cannot prevent that. One connection for writes and a separate read pool should be considered.
- The feed, chat and search paginate by cursor, never by offset.
- Groups: the tables are `groups(id, kind, name, mode, created_at, deleted_at)` and `memberships(group_id, user_id, role, joined_at)`. The role is owner, moderator or member. `posts.group_id` and `messages.group_id` are NOT NULL and reference `groups`. The migration that adds groups creates the root group with a fixed id (`perm.Root`, the one UUID in the system that is not a v7). It assigns every existing post and message to the root group. It turns each user's old `users.role` into their root membership, and it drops `users.role`. A user who is not a member of a group gets 404 from every path under it, never 403, because to them the group does not exist. A comment belongs to its group through its post. A user has no role of their own, only memberships. A group's `last_message_at` is not a column. It is computed when the group is sent (the time of the newest live message), so it cannot drift. A conversation's `people_key` is its set of people, the sorted user ids, and it is unique among live conversations. A membership's `hidden_at` records presence. It is set only in a conversation, never in a room, and it is sent only to that membership's user.
- Soft delete: posts, comments, messages and groups have `deleted_at`. Deleting a post also deletes its comments. There is no tombstone and no orphaned thread (see Simplified). Deleting a group hides everything in it.
- Edit tracking: there is only the `edited_at` flag. There is no version history.
- Unread markers: the table is `read_markers(user_id, stream, read_at)`, with one row per user per stream. The streams are `chat:<group id>` and `feed:<group id>`. A notification is marked read on its own row. The client updates the markers, with a debounce for chat. The markers are stored in the database, so they follow a user across devices and can be used by the digest. The marker is a time, not the event sequence number that this note first specified (2026-11-06). The items counted against it, messages and notifications, are paged and ordered by `created_at` and have no sequence number. A time can be compared with a row without a join to the event log. A marker only moves forward, and it is never set later than the current time.
- Chat history is kept forever and is paginated.
- Time: all times are UTC, always. They are stored and served as Unix milliseconds or as RFC 3339 with `Z`. The server never handles time zones. The browser renders relative times and local dates.
- FTS5 indexes a stored plain-text column, produced by bluemonday's `StripTagsPolicy` from the body. It never indexes the HTML. Insert, update and delete triggers keep the index in sync, which is the documented external-content pattern. Triggers do not backfill, so a `rebuild` runs after any migration that touches the index.

## Mobile

There is no dedicated mobile app. There must NEVER be multiple codebases. The React app is a PWA, and the PWA is the mobile app at launch. On iOS, web push works only for PWAs installed to the home screen, so an install prompt is part of the first version.

Later, Capacitor will wrap the same React build to put the app in the iOS and Android app stores, and it will add native push. This is not part of the first version. Bubblewrap was ruled out because it supports only Android.

The Capacitor shell will **not** share the web app's cookie session. Its iOS origin is `capacitor://localhost`, so every API call is cross-site. `SameSite=Lax` cookies are never sent on those calls. iOS 14 and later block third-party cookies in WKWebView by default. The `WKAppBoundDomains` workaround is limited to ten domains, which is incompatible with a multi-instance app that asks "which Sweet?". The shell will instead send the session id in an `Authorization: Bearer` header. The session store is therefore independent of the transport from the start. The same opaque session id arrives either as a cookie *or* as a header. Supporting the shell later needs a header change, not a redesign. JWTs are not used. "Log out everywhere" needs a server-side lookup anyway, so a self-describing token gains nothing, and it adds signing keys and refresh logic. SSE from the shell is a separate question, to be answered when the shell is built.

## Accounts

**Profiles** (built 2026-11-06). Each user has a profile page at `/u/<name>`. The page shows the user's picture, name, role (runs this community, or moderator) and when they joined. It shows a bio of a few lines. The bio is written in the comment editor, and only the user can edit it (`PUT /api/me/bio`). The bio is sanitised with the same bluemonday policy as other bodies, and it is stored as HTML with its plain text stored beside it. A `profile` event carries the whole profile to every connected client, because every profile is visible to every user on the instance. Another user's profile page has a Message button. The page lists the user's posts, newest first (`GET /api/users/{name}/posts`). Only posts from rooms the viewer is a member of are included, and each post says which room it was posted in. Chat messages are not listed, because chat is a conversation rather than a post. A removed account has no profile page. The hover card is a preview of the profile page, and the name on the hover card is a link to the page. **The account row at the foot of the nav represents the signed-in user** and opens that user's own profile page. Settings is reached from that page. This was Raphael's decision on 2026-11-06. The row did nothing before, and the question "where do I change my picture" now has one answer, which is the place where the picture is shown. On a profile page, the top bar's title is the user's name. On Settings, the top bar's title is a link back to the signed-in user's own profile page. There is no following in the first version. On old Sweet, following was real and mutual. There were 2,086 follow edges among the 212 people who posted, 72% of follows were reciprocated, and the median poster followed 6 of the other 211 posters. However, a following feed shows each person only a small slice of a small community, and that is the opposite of what a community of about thirty people wants from Home. Home shows everyone. If an open instance ever needs following, it will be a separate view behind a feature flag, and it will never be Home. The 3,636 raw follow edges include 1,092 edges to one account, from 851 people who followed nothing else. Those edges were an automatic follow on signup, not a social relationship.


Login and registration use an email address, a username and a password, with email verification. The system does not allow identity enumeration. Registering with an email address that already has an account returns 202, exactly as registering with an unused address does. Changing an unverified account's address to one that already has an account also returns 202. In both cases, the owner of the existing account is emailed about the attempt. Registration validates the invite code before it looks up the username or the address. A request without a valid code therefore gets 404 regardless of the username or address. Failed invite codes are rate-limited per client address in the same way as failed logins. This was decided on 2026-11-08, after an audit found that both endpoints returned 409 "already has an account", and that registration returned it before checking the code. A taken username is still reported, because usernames are public at `/u/<name>`. Password reset is supported. Passwords are hashed with Argon2id at the OWASP minimum parameters (m=19 MiB, t=2, p=1 or equivalent). Verification and reset tokens expire and are single-use.

**Built 2026-11-06.** Registration (`POST /api/register` with an invite code, username, password and email address) creates the account in the unverified state and sends a verification link by email. It issues no session, and the registration page shows a message asking the user to check their email. The verification page at `/verify/<token>` consumes the token (`POST /api/verify`), marks the address as verified and signs the user in. Verifying is the sign-in, so there is no second step. The sign-in form has one field, which accepts a username or an email address. An account with an unverified address is refused with `403 {error: "unverified", email}`, and the sign-in page then shows the same check-your-email screen. From that screen, the user can resend the link with `POST /api/verify/resend {email}`, which answers 202 whatever the address is. The user can also change the address with `POST /api/verify/change {username, password, email}`. The password is required there because the user cannot yet have a session. The old address is discarded, because it was never confirmed to belong to the user. An owner account created at the command line has no email address and is allowed to sign in. Settings asks that owner to add an address. For a forgotten password, `/reset` asks for an email address (`POST /api/reset`). That endpoint answers 202 whether or not the address is known, and it sends a link only to a verified address. The page `/reset/<token>` takes the new password (`POST /api/reset/{token}`), ends every session and signs the user in on the current device. In Settings, a new email address (`PUT /api/me/email {email, password}`) is stored as `pending_email`, and a verification link is sent to it. The old address stays in effect until the link is opened. The link opens the same verify page, which also works while signed in. A new password (`PUT /api/me/password {current, password}`) ends every other session. `GET /api/me/account` returns the address, whether it is verified, and the pending address. Tokens are 32 random bytes. They are stored as their SHA-256 hash in `email_tokens`, with a kind, the address they were sent to, an expiry (one day for verification, one hour for reset) and `used_at`. A token that is of the wrong kind, already used, expired or unknown gets the same response in every case. At most five links of one kind are sent to one user per hour. Requests beyond that are dropped without an error. The endpoints that send mail are rate-limited per client address in the same way as sign-in, but on their own limiter, so that a reset request cannot use up the sign-in allowance. Passwords are hashed with Argon2id at the parameters given above. A hash that begins `$2a$` or `$2b$` belongs to an account from before this change. Such a hash is still checked with bcrypt and is not rewritten, because the owner's account was the only one that existed before the change. The email address is unique per instance, compared case-insensitively, enforced by a partial index on `lower(email)`.

Uniqueness is per instance, because each instance has its own database. Usernames and email addresses are unique within an instance and are compared case-insensitively. Usernames are also Unicode-normalised before comparison. Usernames live under `/u/<name>`, so the reserved list is a small set (`admin`, `sweet`, `moderator`) rather than every route name. Username changes are allowed, because mentions and authorship refer to the user's id. Email changes take effect only after the new address is verified.

If the verification email does not arrive, the user sees a screen that offers to resend the email or to change the address. There is no bounce tracking.

Authentication uses server-side sessions, not JWTs. Sessions are stored in the instance's SQLite database. A session lasts 180 days with a rolling expiry, and the expiry is refreshed at most once a day. The stored session id is the SHA-256 hash of the token the client holds. On the web, the token is held in an httpOnly `SameSite=Lax` cookie set by an HTTP response header. Safari's seven-day cap on cookie lifetime applies only to cookies set by script, so it does not apply here. CSRF protection is the SameSite attribute plus an Origin check on every state-changing request. The same session id can be presented as a bearer token (see Mobile).

Session revocation is a "log out everywhere" action. A user can apply it to their own account. A moderator can apply it to any user. The orchestrator can call it through the instance admin API.

There are per-user rate limits on posting, uploading, login attempts and password resets. Sign-in rate limiting (built 2026-11-06, refined the same day): per client address, five wrong passwords are allowed at once, then one every twelve seconds. When the limit is reached, every login attempt from that address is refused, even with the right password. A correct password, or a refusal because the address is unverified, does not count against the limit, because the limit exists to stop password guessing and neither of those is a guess. At first, every attempt counted against the limit, and the small number of real sign-ins that the browser test suite performs across its two front ends was enough to trigger it. The endpoints that send mail count every call against their limit, and they use their own limiter.

### Registration modes (per-instance setting)

- Invite-only
- Approval

There is no open registration, so no bot protection is needed. In practice, approval mode is open registration.

Approval mode needs a moderator UI. The UI shows a queue of pending applicants, with the time each one applied and their answer to a question set by the instance (for example "how did you find us?" or "who do you know here?"). A moderator can approve or decline each applicant, and the applicant is emailed either way. Moderators receive a notification when someone applies.

The approval answer can also serve as the newcomer's first post. At minimum, it can be shown to members as "X has just joined", so that existing members have something to reply to.

The community's rules are shown at signup, and the applicant must accept them.

## Instance admin API

Every instance exposes a small admin API, authenticated by a per-instance token. The API powers the instance's own admin screens. The orchestrator is one client of this API and has no special access path. The orchestrator never accesses an instance's database directly, so hosted and self-hosted instances run the same software.

## New-instance lifecycle

There are three stages, with a clear boundary between the orchestrator and the instance.

1. **Provision** (orchestrator). The inputs are a name, a subdomain and the owner's email address. The orchestrator creates the instance, starts it and generates a one-time setup link. In v0, Raph runs `sweet create` and emails the link by hand. Later, a web form will do this and the email will be sent automatically. Later, a payment step will be inserted before this stage.
2. **Setup** (inside the instance). The link opens the first-run page. The owner sets a password and verifies their email address. Secrets (the session key, the admin token and the signing key for URLs) are generated on first run and are not shipped in the config.
3. **Onboarding** (inside the instance). The owner sets the name, description, rules, registration mode, feature flags and topics, and is then prompted to invite their first people. Onboarding ends on the empty feed with a prompt to write a first post.

Stages 2 and 3 are implemented in the binary. Self-hosters therefore get the same onboarding, and the orchestrator stays simple.

**Stages 2 and 3 built 2026-11-06.** Each instance is a separate process of the single binary, running on its own database. `sweet create` (stage 1, not built) will start that process and pass on its setup link. When the binary starts with no owner account that can sign in, it generates a setup token and stores the token's hash in the settings table. It prints `SETUP: … <base-url>/setup/<token>` to its log, and the sign-in page shows a message that the community has not been set up yet. The setup page (`POST /api/setup {token, username, email, password}`) creates the owner's account, signs the owner in and consumes the token. The owner's email address is recorded as verified without a verification email. The reason is that whoever holds the setup link controls the server, and a newly created server may not have email configured yet (Raphael, 2026-11-06). If an owner account created at the command line without a password already exists, the setup page reuses that account instead of creating a second one. `-owner-password` remains the scripted way to create the owner, used by the tests and by a self-hoster's script. When it is used, no setup link is printed. Onboarding is the welcome page. The client shows this page to the owner while the community has no name. The page asks for the name, what the community is for, and who may create rooms. It uses the same form as the Community page, so the two cannot disagree. It then shows an invite link to copy, and then a "Go to <name>" button that leads to Home. A member cannot exist before the community has a name, because only the owner can create invites.

### Domains

In v0, each instance is at `theirgroup.sweet.community`, covered by one wildcard certificate obtained through Caddy's DNS challenge. The Cloudflare DNS module is not included in stock Caddy. The compose stack therefore ships a Caddy image built with xcaddy, and upgrades must keep that image. Custom domains will come later, using on-demand TLS. On-demand TLS requires an `ask` endpoint that answers whether a given domain belongs to us. The orchestrator provides that endpoint.

## Data export

Data export is supported from the start as a fundamental part of the API design. There are two exports. The per-user export is for personal export. The per-instance export is for migrating to a new instance. The export format is the import format. Import is built first, because import is what tests the export.

The two exports have different shapes. The per-instance export is the SQLite file plus media, with a schema version. Importing it runs the SQL migrations forward. The per-user export is a versioned JSON document plus media. Bodies in it are the stored HTML. It has its own small forward-migration path.

## Orchestrator

Version one of the orchestrator is a CLI on the hosting server. `sweet create <name>` writes a config, starts the binary and adds the Caddy route. There are also stop, start, read-only, upgrade and destroy commands. A web UI for the superadmin will be added when there are more instances than one person can keep track of from memory. Billing comes later. The orchestrator is kept simple and outside the instance boundary (see Instance admin API).

## Config

The design was one TOML file per instance with environment-variable overrides. Secrets are generated on first run. Migrations are embedded in the binary, are forward-only, and run on start. A `VACUUM INTO` copy of the database is taken before they run, so that a bad migration can be recovered from. That copy is the upgrade backup. `sweet upgrade` does not take a second one.

**As built (2026-11-06):** there is no TOML file. Every setting is a command-line flag with a corresponding environment variable, and `-help` lists them. The compose stack's `.env` file is the one file an operator edits. A TOML file would be a second place for the same settings, and the orchestrator, when it exists, can write environment variables just as easily. The copy before migrations is built. When a database that has been migrated before has pending migrations, `Migrate` first writes `VACUUM INTO <db>.before-upgrade` beside the database file, replacing the previous copy. There is therefore always exactly one copy, from the most recent upgrade. A fresh database is not copied. `-trust-proxy` (`SWEET_TRUST_PROXY=1`) makes the first address in `X-Forwarded-For` the client address for the sign-in and mail rate limiters. Without it, behind a proxy, every user would share one rate-limit budget. It is off unless the operator turns it on, because anyone can send that header. `-litestream` (`SWEET_LITESTREAM=1`) sets the `wal_autocheckpoint=0` described in the Backups section.

## Updates

- **Hosted:** `sweet upgrade <name|all>` stops the instance, swaps the binary, starts the instance and checks `/healthz`. On start, migrations run after their `VACUUM INTO` copy is taken. On failure, the copy and the old binary are restored. Our own instance is upgraded first, then everyone else's. Instances are pinned to versions, so a bad release stops at one instance.
- **Self-hosted:** replace the binary and restart, or upgrade with apt via the Debian package. The binary refuses to start against a database that is newer than the binary.
- **Clients:** the frontend is embedded in the binary, so the API and the UI cannot drift apart except in tabs that were already open. The SSE stream sends a `version` event on connect. A tab that loaded a different version reloads.

**Built 2026-11-06.** The version identifier is derived from the binary itself. `internal/version` computes it as a hash of the binary's own bytes. Nothing is stamped in at build time, two builds of the same source produce the same version, and any other build produces a different one. `sweet -version` prints it. The stream writes `event: version` before any other event, with no id, so it never changes `Last-Event-ID`. The tab keeps the first version it receives and reloads when it receives a different one. A Go test reads the first lines of the stream. A Vitest test drives the hook with a fake `EventSource`. The Playwright flow cannot start a second binary in the middle of a test. Instead, it answers the tab's first connection with a stand-in stream that names an older version, and the real server's response on reconnection then acts as the upgrade. In the compose stack, an upgrade is `git pull`, then `docker compose pull`, then `docker compose up -d`. The old container stops, and the new one takes the pre-migration copy, migrates and starts. **The image is published, 2026-11-07.** The repository is github.com/lowercasename/sweet-community. `.github/workflows/image.yml` runs `go test` and the web checks on every push, then builds the image for amd64 and arm64 and pushes it to `ghcr.io/lowercasename/sweet-community` as `latest` and `sha-<commit>`. The Dockerfile builds the frontend and the binary on the build machine for the target platform. The compose files name that image. `SWEET_IMAGE` in `.env` pins a specific image, and that is how a bad upgrade is backed out. Playwright does not run in the workflow yet, because it needs the browsers installed on the runner. The Debian package and the hosted `sweet upgrade` are not built.

## Backups

Litestream runs alongside the binary, tails the SQLite WAL and streams every change to the instance's S3 bucket. Restore granularity is exact for the most recent minutes. Older points can be restored at roughly five-minute boundaries, because L0 files are compacted away after the default retention of five minutes. Replication is asynchronous, so a crash loses about the last second of changes. The following operating rules go in the self-host documentation. The app sets `PRAGMA busy_timeout` and `synchronous=NORMAL`. Litestream owns checkpointing, so the app sets `wal_autocheckpoint=0`. The database must be on a local disk on the same host, never on a network filesystem or a Docker Desktop volume. There must be one Litestream process per replica path. R2 works through the generic S3 endpoint with an R2-scoped API token.

For self-hosters, Litestream is optional. The fallback is a nightly `VACUUM INTO` copy uploaded to S3 by a goroutine in the binary, which needs no setup. Media is already stored in S3, so the database is the only thing that needs backing up.

**Built 2026-11-06 in the compose stack.** Litestream runs in the same container as the binary, not in a separate container. `litestream replicate -exec` supervises the binary. There is therefore one container, one volume and one set of settings, and Litestream and the binary cannot be pointed at different database files. One bucket per instance holds both the images and the database. Images are under `images/`, which is the `SWEET_S3_PREFIX` that the entrypoint sets. The database is under `db/`. This means one bucket and one token to create, and one thing to delete when the instance ends. The bucket is private in either case, because images are served through the binary. The same `SWEET_S3_*` settings configure both. Setting them turns on both image storage in S3 and database backup. Without them, images stay on disk and nothing is backed up. The README states this in those words. At start, `litestream restore -if-db-not-exists -if-replica-exists` restores the database when the disk has none. This is how a new host takes over as the old instance. `docker compose run --rm sweet restore [timestamp]` performs a point-in-time restore. The nightly fallback is not built. With the bucket optional and the setup a single line, there was no remaining case that needed it.

## Email

The code sends email over plain SMTP. The host, port, credentials and from-address are in the config. Hosted instances use Mailgun's SMTP endpoint. Self-hosters can use any SMTP server. The Mailgun API is not used.

Email was built on 2026-11-06 as `internal/mail`. It defines a `Sender` with two implementations. The SMTP implementation is configured by `SWEET_SMTP_HOST`, `_PORT`, `_USER`, `_PASSWORD` and `SWEET_MAIL_FROM`. It uses `net/smtp` with PLAIN authentication and STARTTLS when the server offers it. The directory implementation (`-mail-dir`, default `data/mail`) is used when no SMTP host is set. It writes one file per message, named `<unix ms>-<n>-<address>.txt`, containing the headers and then the text. Development and the tests read these files. The Playwright helper that creates a member reads the verification link out of one of these files, so every flow a test runs is the same flow a person runs. Links point at `-base-url` (`SWEET_BASE_URL`). Messages are plain text, with one recipient and no templates. Three such messages exist.

**One template, 2026-11-07.** Raphael asked for emails that are pared down, responsive, quick to read and consistent. Every email is built from `mail.Content`. Its parts are the community's name (or Sweet, before the community has a name), a heading, a few short lines, at most one link, and a note. It renders a plain-text version and a single-column HTML version. The HTML uses inline styles, system fonts and no images, and it shows the one link in Sweet's red. A message carries both versions and is sent as `multipart/alternative` with the text part first. The directory implementation writes the text file that the tests read links from, and writes the HTML beside it. The verification and reset emails use this template and name the community in their subjects. The digest email does the same.

## Search

Search is very important. Search uses SQLite FTS5 over posts, comments and chat messages. Results are scoped to what the searcher is allowed to see, through the visibility function. The index covers each row's `body_text` column, which holds the plain text extracted from the body when it is written. Triggers maintain the index, so it cannot drift from the source rows. Chat is searchable.

**Built 2026-11-06.** There is one FTS5 table, `search`, over the plain text of posts, comments and messages. Beside the text, each row carries the kind, the id, the group, the post, the author and the time as unindexed columns. Insert and update triggers on each source table keep the `search` table in step with the source rows. When an item is deleted, its text is removed from the index. When an item is edited, its text is replaced. When a post is deleted, its comments are removed from the index with it. The migration backfilled the table from the existing rows. The table stores its own copy of the text. It does not read the source tables as FTS external content, which is what this document first specified. The reason is that the source rows are keyed by UUID and have no stable rowid for FTS to reference, and the text is small. `GET /api/search?q=` is the one query that sqlc does not generate, because it reads a virtual table. It is written by hand in `search.go`. The typed query is converted into quoted words, all of which are required, so the FTS query can never be a syntax error. The index uses trigram tokens (migration 020). Trigrams replaced word-start matching after an hour of using it. With trigrams a word matches any part of a word, so "armalade" finds "marmalade". Raphael chose this on 2026-11-06 and accepted the larger index, which is roughly three times the size of the text. A word of fewer than three characters cannot be matched by trigrams and is dropped from the query. If no words remain, the endpoint returns a 400 that says so. The excerpt is sixty-four trigrams, about one line, because `snippet` counts tokens. Hits are joined to the searcher's current memberships. Hits are ordered by FTS5's rank, which is bm25. Under bm25 a hit ranks higher when its words are rarer and when more of them appear in a shorter text. Recency plays no part in the rank. At most fifty hits are returned and the results are not paged, because rank is not a cursor and fifty is more than anyone reads. A hit carries an excerpt in which the matches are marked by two control characters. The client renders the marked spans as bold. No HTML crosses the wire. The page at `/search` keeps the search words in the `?q=` query parameter, so a search survives a reload and its URL can be sent to someone else. The search box is the full width of the page, with no label and no button. Pressing Enter runs the search. The earlier design, a labelled field with a large button beside it, looked like a form rather than a search box (Raphael, 2026-11-06). Each hit's line shows the author first, then the content and its location, then the time. Opening a hit opens its post. For a message, opening the hit opens its room.

## Notifications

There is one in-app notifications table. Every delivery channel reads from it.

**A notification records one action done to one person** (built 2026-11-06). It is a row in `notifications` for that person. The handler that writes the action writes the row in the same transaction. The client never writes a notification. No notification is created for a user's own actions. Two kinds existed at first. `comment` means someone commented on your post, and goes to the post's author. `added` means someone added you to a room, and goes to the person who was added. Later kinds are `mention` (added with mentions, 2026-11-06), `joined` (the owner is notified when someone joins through an invite, 2026-11-06), `topic_post` (2026-11-07, notifies a topic's followers of a new post in that topic, see Topics) and `message` (2026-11-08, below). A new post in a room and a new message in a room's chat are not notifications. They are *unread* items, described below. A message in a conversation is both a notification and an unread item (2026-11-08, below). The row carries the actor, the location as `group_id` and, for a comment, the post. The client composes the text, for example "mo commented on your post" or "raphael added you to Knitting". If the user is no longer in the room, the client writes "to a room" instead of the room's name. The client also determines the destination, which is the post's page or the room. `GET /api/notifications` returns the requesting user's notifications, newest first, paged in the same way as the feed. A new or updated row is sent as a `notification` event, delivered only to the person the notification is for. Deleting notifications uses a separate event, `notification_delete`, described below.

**A notification is marked read when the user opens it** (Raphael, 2026-11-06, reversing that morning's rule that viewing the page marks everything read). `PUT /api/notifications/{id}/read` sets `read_at` on the row. The page calls it when it opens the notification's target. The response and the event both carry the updated row, so every client shows the same state. Viewing the notifications page marks nothing read. The page's New section holds the unopened notifications, and while it is not empty the notifications dot stays lit. The Earlier section holds the opened notifications. The Clear action calls `DELETE /api/notifications`, which permanently deletes the opened notifications and never an unopened one. One `notification_delete` event names the deleted set as `{user_id, before}`. It is the only delete event without an id, because the set, meaning the opened notifications up to that time, is exactly defined by those two values. The notifications dot is driven by the count of unopened rows. That count is carried as the `unread` value of the notifications stream on `GET /api/markers`, which is the client's single source of unread counts. The notifications stream has no read marker.

**Read markers are for chat and feeds.** The table `read_markers(user_id, stream, read_at)` records how far along a stream a person has read. There is one row per person per stream. A marker only moves forward. `PUT /api/markers/{stream}` sets `read_at` to the current time and keeps the later of the existing and new values, so a stale tab cannot mark as unread what another tab has already read. The update is sent back as a `marker` event to that person only, so every device shows the same state. The streams are `chat:<group id>` and `feed:<group id>`. A group the user is not a member of has no streams for that user. For a few hours the notifications stream also had a marker, and viewing the page moved it. That marked every notification read as soon as the page was viewed, which is not what reading a notification means, so the marker was removed.

**The notifications indicator is a dot, never a count** (Raphael, 2026-11-06). The nav's Notifications item and the phone's Notifications tab show a dot on the icon while the user has at least one unopened notification, and their accessible names include "unread". A count invites the user to clear it. A dot only indicates that something is new. Both the nav item and the tab open the page at `/notifications`.

The following were planned in this order and built overnight from 2026-11-07 to 2026-11-08:

- A weekly email digest for anyone who has not visited. It contains counts and metadata only. The counts are how many posts were made, in which topics, who joined, and how many replies the user received. They are counted from the user's read markers. The email also contains a link. It contains no post content and no images. The digest was built before push, because it is what brings back people who have gone quiet.
- Web push for mentions and replies to the user's posts. On iOS, push reaches installed PWAs only.
- Both are configurable per user, with "off" one click away.

**The digest, built** (`internal/digest`, migration 023). An hourly job inside the binary finds every user who is due a digest. A user is due one when all of the following hold. They are in the community. They have a verified email address. They have not turned the digest off. No session of theirs has been seen for seven days. No digest has been sent to them for seven days. There is something to report. The "since" time for the counts is the later of the user's feed read marker and the time of the last digest, so a week's counts are never repeated. The email uses the one email template. Its body is at most three lines. The first line reports new posts by others and their topics, for example "12 new posts: 5 in Practice, 3 in Reading, 4 without a topic." The second line reports replies to the user's posts. The third line reports who joined. After the lines come a link to the community and a note saying how to turn the digest off. If there is nothing to report, no email is sent and nothing is recorded, so the next hourly run checks the user again. The digest is tested with a fake sender and a fixed clock.

**Web push, built** (`internal/push`, `web/public/sw.js`). The instance generates its VAPID key pair on first start and stores it in settings. A device subscribes from the Settings page. The client fetches the key with `GET /api/push/key`, sends the browser's own subscription with `POST /api/push/subscriptions`, and unsubscribes with `DELETE`. There is one row per endpoint. After a write's transaction commits, the server looks at the notifications among the write's events. Each one that is a mention or a comment on the person's post is pushed to every device of that person. The push is sent outside the request's path. It carries a title, which is the community's name, a line such as "mo commented on your post", and the post's URL. It is sent through `SherClockHolmes/webpush-go`. When the push service responds 404 or 410 for a device, that device's subscription is deleted. The service worker displays the push notification and opens its URL when the notification is tapped. The service worker caches nothing, so the app always matches what the server serves. The web app now has a manifest and icons, which iOS requires before it allows push to an installed app. The icon is the S mark. It is the Ubuntu Bold S glyph as an SVG path on a red disc, centred on the glyph's bounding box, and rasterised with Chromium. An earlier version drew the S as SVG text. It sat too high and used whatever font the viewer had installed (Raphael, 2026-11-08). There is no install prompt yet. The Settings page shows a line telling an iPhone user to add Sweet to the home screen first. No other kind is pushed. A `topic_post`, being added to a room and someone joining stay in-app only.

**A message in a conversation creates a notification** (Raphael, 2026-11-08, reversing the earlier decision that a message is unread only). The conversation keeps its unread dot. The notifications page also shows "mo messaged you", so a person who is not in the app is notified in the same way as for a mention. Two rules stop this from duplicating the unread dot. *At most one unread row per conversation.* While a user has an unread message notification for a conversation, further messages in that conversation write no new row. After the user reads the conversation, the next message writes a new row. *Marked read by reading the conversation.* `PUT /api/markers/chat:<id>` also marks every message notification for that conversation up to the marker time as read, in the same transaction. Each updated row is sent as a `notification` event. These are followed by a `marker` event for the notifications stream carrying the new unread count. The count is needed because a client that has not loaded the notifications list cannot derive it from the row events. The browser test found this on 2026-11-08. Opening the row from the notifications page opens the conversation, which moves the marker, so both paths end in the same state. The row carries no message content and links to the conversation. It is the sixth notification kind, `message`. Migration 024 rebuilds the table to extend the CHECK constraint. Room chat remains unread only, without notifications, because a notification for every message in a room would duplicate the room itself. A member who has hidden the conversation gets no notification. The push notification is sent from the row. It is tagged with the conversation id, so a device shows one notification per conversation. Its text is "mo messaged you". The service worker does not show a push for a conversation that is open in a focused window. A notification that is already read when it is sent as an event is not pushed. The digest includes a line such as "2 conversations with new messages". It counts conversations with messages from others that are newer than both the user's chat marker and the last digest.

**The wordmark has two sizes** (Raphael, 2026-11-08, completing his own change). The wordmark is Sweet's S in a red circle with a label next to it. At both sizes the letter's cap height is about two fifths of the circle's diameter, which is the same ratio as the app icon. The gap between the mark and the label is 8px, the same as the nav's gap. The `md` size is used in the sidebar header. It has a 32px mark and the community name in red bold. The label starts at the same x position as the nav item labels. When the sidebar is collapsed, the mark is centred on the nav icons (measured 2026-11-08). The `sm` size is used for the credit under the auth pages. It has a 20px mark and "Made with Sweet" in grey. The auth page layout changed at the same time. The community name is now the heading above the card instead of a wordmark inside the card. ## Admin tools at launch

In copy shown to users, the instance is called **a community** (Raphael, 2026-11-06: "this place" became "this community" in every line of copy). Rooms are inside the community. The word "place" remains only as this document's term for the nav's first block, which lists the things a user can be a member of.

The roles are owner, moderator and member. They are stored as memberships of the root group. See Groups, where the same three roles exist in every group. There is one owner, who is the person who runs the community. The owner sets any user to member or moderator from the People page. A moderator can delete any content and cannot edit other users' content, exactly like the owner. A moderator can create and revoke invites. Invites add people to the root group. A moderator cannot change roles. Handing over ownership is an explicit action by the owner. It works on the root group in the same way as on any other group. The former owner becomes a moderator. A role change is sent as a `membership` event carrying the whole membership row, including the joined time. A response that once omitted the joined time caused the client to display "joined 1 Jan 1970". Because the event carries the whole membership, the controls on every open page update to match it.

**Removing a user** (built 2026-11-06, as specified above). Staff remove users below their own role from the People page. A moderator can remove members. The owner can remove members and moderators. Any user can remove themselves from the Settings page. Nobody can remove the owner. The owner must hand over ownership first. The rule is `perm.RemoveFromInstance`. The people list carries `can.remove` computed for the viewer, so the page makes no permission decision of its own. A removed user is always anonymised and never deleted. The account's row stays, so their content keeps its author id. The username becomes `removed-<the id's random tail>`. Nobody can register a username with the `removed-` prefix. The password and picture are deleted. Their sessions are ended. An open page belonging to the removed user receives the `membership_delete` event for its own root membership and signs itself out. Each room they owned passes to a new owner by seniority. The longest-serving moderator becomes owner. If there is no moderator, the longest-serving member becomes owner. The change is sent as a `membership` event. If the removed user was the only member, the room closes. Their conversations keep the removed user in the member set, hidden, so the conversation shows the name as removed. The `user` event is sent first. The client updates the author name on the removed user's posts, comments and messages in every loaded feed, thread and room, so the anonymisation shows at once, whether or not the people list is open.

Minimum shipped:

- Invite link creation and revocation
- The approval queue
- Remove a member, whose content is then anonymised
- Delete any post, comment or message
- A pinned instance-wide announcement
- A view of recent signups
- Log out everywhere, for any user
- Unanswered posts, a list of posts with no reply yet, oldest first. Old Sweet's data showed that a reply within a week was the clearest difference between people who stayed and people who left.
- Instance settings. These are name, description, welcome message, rules, feature flags, topics, registration mode and source-code link.

**The community's name (built 2026-11-06).** `name` and `description` are rows in the settings table, alongside `group_creation`. `GET /api/settings` is public, because the sign-in, join, verify and reset pages show the name before any session exists. The response also carries `owner_set`, which is state rather than a setting. The `PUT` on the same endpoint is restricted to the owner. It requires a name of at most sixty characters. The description is at most five hundred characters. It broadcasts the whole settings row as the existing `settings` event, which every connected client receives, so a rename reaches every open page at once. The community's name replaces "Sweet" in the nav's header and in the browser tab's title. Sweet's mark, the S in the red circle, remains the product's mark. The pages that a visitor who is not signed in sees show "Made with Sweet" in small text under the card (Raphael, 2026-11-06). The join page states who invited the visitor, to which community, and what the community is for. The owner edits these settings on the **Community** page. It appears in the nav after People, and only the owner sees it. A page about the community does not belong behind the owner's own page, where Settings is (Raphael, 2026-11-06: "that feels confusing"). The Settings page keeps only what belongs to the user themselves. Those are picture, account, sign out and leaving the community.

**Invite links can be used many times** (Raphael, 2026-11-06). The reason is that a group of people moves to a new community together, and one link per person would not bring them. A link is valid for anyone who has it, for seven days. It counts the users who joined through it in `uses`, which the People page shows as "N joined through it". Its creator can revoke it. `used_at` stays null and is no longer read. The owner receives a `joined` notification for each user who joins. It links to the new user's page. Nobody else receives it, including moderators. This reverses the first version, in which a link was consumed by its first use.

Nothing more elaborate will be built until a real instance asks for it.

## Instance lifecycle (ending)

When a group stops paying or asks to close, the instance becomes read-only for 30 days and shows a banner. During those 30 days the instance export is available to the owner and personal exports are available to every user. After the 30 days the instance stops. The database and media are kept for a further 60 days and then deleted. This is stated on the pricing page.

Read-only mode is also available as a switch on self-hosted instances, because a community can wind down regardless of how it is hosted. The numbers 30 and 60 are provisional. The structure of the process is the decision.

## Visibility rules

There is one Go function, `CanSee(viewer, thing)`, and every query path goes through it. A table-driven test file covers each viewer state against each thing type. The viewer states are anonymous, member, moderator, author and removed. The thing types are post, comment, chat message, image, group and topic. No feed query may bypass `CanSee` for performance until a test proves that the bypass gives the same answer. This rule is non-negotiable, because it is the promise the product makes.

The rule itself is membership and nothing else. A signed-in viewer who has not been removed can see a thing if they are a member of the group the thing is in. Staff have no additional visibility. List queries are scoped in SQL by a join on `memberships` for the viewer. Single-item reads go through `CanSee` in `internal/perm`. A test checks that the two agree.

## Permissions

Permissions are the write side of the same promise, built in the same shape. One package, `internal/perm`, holds every rule about who may do what to what. The rules are `EditPost`, `DeletePost`, `EditComment`, `DeleteComment`, `DeleteMessage`, the group and membership actions, and `CanSee`. Each rule is a plain function. Its inputs are an actor, meaning the actor's id and their role in the thing's group, and the thing's ownership facts. One table-driven test covers the rules, with one row per (who, what) pair. Every write handler fetches the thing's owners and the actor's membership, calls perm, and responds 403 if the answer is no. No query carries an author clause of its own. Because roles are stored on memberships, the same functions serve the root group and every other group.

The frontend holds no permission logic. Every post, comment and message the API serves carries `can: {edit, delete}`. Every group carries `can: {add_members, remove_members, set_roles, rename, delete, leave}`. perm computes these flags for the requesting user as the response is built. Menus and buttons show what the flags say. There is nothing to keep aligned, because there is only one implementation. A membership change arrives as a `membership` event, and the client refetches what it holds for that group. Mirroring the rules in TypeScript with a shared test table was considered and rejected. Two implementations of a rule will drift apart, which is how old Sweet got four body formats.

## Client data

One cache, TanStack Query, holds every piece of server data the client has. That data is me, users, posts, comments, messages and invites. Components render from the cache and keep no server data in their own state. The event stream is the cache's write path. Each event is one upsert into the cache or one delete from it. A reconnect invalidates everything in the cache. That is the only refetch the app needs while the stream is connected. Users are normalised. Posts, comments and messages render their author from the users query by id, not from the author snapshot they arrived with, so a changed picture, name or role shows everywhere at once. Pagination is cursor pages inside the cache, as infinite queries, and never component state. Feeds, rooms and member lists are cached per group. The people list and the list of the user's groups are cached instance-wide. When the user is removed from a group, the client drops that group and everything cached under it. When the user's own role in a group changes, the client refetches that group's content, because every `can` flag in it has changed.

## Testing and operations

- The failing test is written first, for every behaviour change. Go tests cover handlers, rules and sweeps. Vitest with happy-dom and Testing Library covers pure functions and component state. Playwright covers flows through the real browser against the real binary. This rule exists to prevent bugs that are found after the fact.
- Playwright (`web/e2e`, `make e2e`) runs the product's flows end to end. The flows are sign in and join, posts and comments, chat, images, layout and drafts, groups and DMs, roles, and routing. They run at desktop and phone width. They run against the built binary on a fresh database, and the same flows run against the Vite dev server, because dev mode, with React StrictMode and hot reload, is where Raphael uses the app. The suite exists for bugs that occur between pieces that each pass their own tests. Examples are a class whose rendered effect the DOM tests cannot see, an ordering problem between a stream event and a response, and a page rendered twice. This reversed the earlier decision of "no browser suite" on 2026-11-05, after two such bugs in two days.
- A change is verified on every surface it touches, not only the one it was made for. A layout change is verified at phone width as well. A data-shape change is verified everywhere that data is shown. Tests live in the repo. A check that only ran once on a laptop does not count.
- The S3 image driver has a round-trip test, `TestS3RoundTrip`. It runs against the configured bucket when `.env` names one, and `make test` exports that configuration. Otherwise the test skips. It writes under its own prefix and cleans up after itself. It was verified against R2 on 2026-11-04.
- API-level tests run against a temporary SQLite file per test, created in `t.TempDir()`, with the production pragmas WAL and busy_timeout. They do not use `:memory:`. An in-memory database is per-connection, so a connection pool sees N empty databases. It also cannot run WAL, so the write-contention paths would never be exercised.
- Operations tooling is `/healthz`, structured logs and an optional error-reporting hook. Nothing more is provided.

## Legal

For hosted instances, we are the data processor for every instance. One privacy policy and one set of terms cover all hosted instances. They are written before the first paying group. There is an age minimum. The session cookie is essential, so no cookie banner is needed.

For self-hosted instances, the host is the data controller and we are a software vendor holding no data. The binary ships a configurable privacy-policy page and a rules page, each with template text.

### Simplified

| Was | Now | Why |
|---|---|---|
| A gallery node in the TipTap schema that contains image nodes | Image nodes only. Adjacent image nodes render as a gallery | The result is the same, with one fewer node type and no nesting rules |
| Server-side HEIC decoding | The server accepts JPEG, PNG, WebP and GIF, identified by magic bytes, and rejects other formats with a clear error message | Decoding HEIC in Go needs cgo and libheif. WebKit transcodes HEIC to the first type in the `accept` attribute when JPEG is listed first and `image/*` is absent |
| An in-memory SSE replay buffer | The browser's `Last-Event-ID` header and the `?since=<seq>` parameter are both served from SQLite. The stream also has a heartbeat, and the client forces a reconnect on visibility and online events | SQLite already holds every event, so a buffer would duplicate it. iOS closes sockets without notifying the page, so the client cannot trust `readyState` |
| Member removal with a choice between keeping, anonymising or deleting the member's content | The content is always anonymised | There are fewer branches in the code, and fewer options for the moderator to consider |
| A deleted post left a tombstone so that its comments survived | Deleting a post deletes its comments with it | The author asked for the post to be removed. A placeholder that says "deleted" with other users' replies under it is an unsatisfactory compromise. The cost is that commenters lose their comments. This cost is small in a group of people who know each other. The rows are kept by soft delete in case a moderation case ever needs them |
| A session list UI where sessions are revoked one at a time | A "Log out everywhere" button | One control covers the real use cases, which are a lost phone and a suspected account compromise |
| JWTs | Server-side sessions stored in SQLite, with a rolling 180-day lifetime. The session is presented as a cookie on the web or as a bearer token elsewhere | Sessions are simpler and can be revoked. There is no refresh-token exchange |
| WebSockets / Socket.io | SSE for server-to-client events and plain POST requests for client-to-server writes | SSE is plain HTTP. Proxies and cookies work without special handling, and the browser reconnects on its own. Socket.io is a Node-centric protocol layer that solves a problem from 2012 |
| Bubblewrap | Capacitor, if a native app is built later | Bubblewrap is Android-only |
| The Mailgun API | Plain SMTP, with Mailgun set in configuration | Self-hosters can use any email provider. No vendor is named in the code |
| Docker Compose as the architecture | A single Go binary. Compose is the distribution artefact that packages it | The binary is the unit that a self-hoster installs and that a Debian package wraps |
| Redis | In-process pub/sub | Each instance runs as one process, so there is no need for a message broker |
| A dedicated mobile app, or cross-platform React | A PWA from the same codebase | React Native is a second UI codebase in practice |
| Embeds rendered as live iframes | A click-to-play placeholder with a thumbnail stored locally | This keeps third-party trackers off a private instance's pages by default |

### Considered and rejected

| Option | Why it was tempting | Why not |
|---|---|---|
| TypeScript end to end (Bun, Hono, Zod, `generateHTML` on the server) | One language. The editor's own extensions would render on the server, so the schema could not drift. Zod schemas would be shared between client and server | It loses the small portable binary. Each instance would use 50–80 MB of memory when idle instead of 10–20 MB. Dependency churn in npm was the source of old Sweet's instability. This option is kept as the fallback if the Go walker proves difficult to maintain |
| Go plus a Node TipTap sidecar | Server-side HTML rendered by the real TipTap renderer | It needs two runtimes and a second codebase that must be kept in step with the editor |
| The client sends plain text and a mention list alongside the JSON body | It avoids the recursive walker | Search and notifications would be derived from data that the client controls. The body would exist in two versions that can disagree |
| ProseMirror JSON as the canonical body, validated by a Go allow-list walker | The principle of never trusting client HTML, and structured bodies | It was built on the false premise that Go had no good HTML sanitiser. The walker needed value validation for every attribute, a harness to keep fixtures in sync, a React node renderer and a separate email renderer. bluemonday replaces all of these with one policy |
| JWTs (raised twice) | A token carried in a header for the native shell | A header solves the transport problem. The token format does not matter for that. Revocation needs a server lookup in any case, so JWTs add signing and refresh with no benefit |
| Hand-written SSRF checks | Control over the URL fetcher | A safe-URL library does the same job with one import |
| Markdown as the canonical format (goldmark) | Go-native rendering with no sanitiser needed | Mentions by id, image ids, embeds and alt text have no Markdown syntax. A custom syntax would have to be invented, and the editor round trip would lose fidelity |
| Third-party Go ports of ProseMirror | They would save writing the walker | They are individual projects, not an ecosystem. Each would be a dependency to audit before trusting, and the walker is about sixty lines of code |
| Cookie sessions shared with the Capacitor shell | One authentication path | The `capacitor://localhost` origin makes every request cross-site. iOS blocks third-party cookies in WKWebView. `WKAppBoundDomains` is limited to ten domains |
| UUIDv7 alone as the SSE cursor, with no sequence column | One fewer column | With a connection pool, the order in which ids are generated is not the order in which rows are committed, so a client can skip an event. The integer sequence was reinstated |
| Signed URLs for images in email | Thumbnails in the digest email | The digest carries counts and metadata only, so no images are sent outside the web app |
| GPL-3.0 | Copyleft without the corporate resistance that AGPL meets | It gives no protection at all against a competitor that runs a hosted version |
| MIT / Apache-2.0 for the server | Adoption with no licensing obstacles | Anyone could run a closed, modified hosted version and never contribute changes back |
| Source-available licences (BSL, SSPL, FSL) | The strongest protection against hosted competitors | They are not open source. Debian and Fedora do not package software under them. Communities fork projects to get away from these licences |
| A CLA alongside AGPL | It preserves the option to relicense | A CLA is read as a means to dual-license later. It alienates the kind of contributors that make up this project's audience |

The setup page also chooses the username, so the name given by the flag is used only on the scripted path |
| Where the instance's settings live | A card on the owner's Settings page | A Community page in the nav, shown to the owner | The Settings page had moved behind the owner's own page, and a page about the community in that location was confusing (Raphael, 2026-11-06) |

A stock image is one fewer thing to build and keep up to date (Raphael, 2026-11-06) |
| Litestream's place | A separate service running beside the binary | Inside the binary's container, as the process that supervises the binary | There is one container, one volume and one `.env` file, so Litestream and the binary cannot disagree about which database file they use |
| Instance config | A TOML file, with environment variable overrides | Environment variables only, from one `.env` file for the whole stack | A config file would be a second place for the same settings |
| Topics | Exactly one topic per post, chosen from the owner's list, with a default topic so that nobody had to choose | At most one topic per post, and most posts have none. An empty topic list means topics are off | A default topic put a topic pill on every post and made following that topic meaningless (Raphael, 2026-11-07) |
| Staff and other users' posts | Staff could delete a post but never edit it | Staff may also change a post's topic | Moving a post to the correct topic is moderation, not rewriting the post (Raphael, 2026-11-07) |
| Copy | Copy described how the software worked (the server's log, where a hidden conversation goes, who a room's ownership passes to) | Copy explains Sweet's own terms at the point in the interface where a user first meets them, and never describes the implementation (see CLAUDE.md, Copy) | Copy is read by users, who do not need to know how the server works (Raphael, 2026-11-07) |
| Composer | A "Set topic" pill next to the Post button, shown while the feed was showing all topics | No topic control in the composer. A new post takes the feed's currently selected topic | The pill in the feed header already selects the topic. A second control for the same choice was confusing (Raphael, 2026-11-08) |
| Messages | A message in a conversation counted as unread only, and never created a notification | A message also creates a notification. There is at most one unread message notification per conversation, and it is marked read when the conversation is read | A user who is not in the app needs to be notified that someone messaged them, and notifications are the only mechanism that reaches them (Raphael, 2026-11-08) |

### Corrections from the adversarial review (Nov 2026)

The following claims in earlier drafts were wrong. Each entry gives the claim and what replaced it.

- "Go has no good HTML sanitiser". This was false. bluemonday is maintained. This correction reversed the body-format decision (see Reversed).
- "The same cookie works in a Capacitor shell". This was false. See Mobile. The session store was made token-agnostic.
- "A monotonic UUIDv7 makes the id a safe SSE cursor". The order in which ids are generated is not the order in which rows are committed. The integer sequence was reinstated.
- Litestream provides "point-in-time restore". Beyond the most recent minutes, the restore granularity is roughly five minutes. See Backups.
- "iOS converts HEIC to JPEG when the file input accepts JPEG". It does so only when JPEG is the *first* listed type and `image/*` is absent. Android does not transcode at all.
- "A private IP range check prevents SSRF". The check is insufficient on its own. It was replaced by a safe-URL library.
- "Use in-memory SQLite for tests". An in-memory database is per-connection and has no WAL. Tests use temporary files instead.
- "busy_timeout handles write contention". It does not handle deferred transactions that read and then write. `BEGIN IMMEDIATE` is used everywhere.
- An image proxy with a session check contradicted thumbnails in email. This was resolved by making the digest email content-free.
- The allow-list walker was described as checking names only. It would have had to check values as well (href schemes, ids, numeric bounds). It was superseded by bluemonday's policy, which checks values.
- Caddy's Cloudflare DNS module requires a custom build. It is not in stock Caddy.
